## 2026-08-09 주간

- **push 실패의 원인은 토큰 만료가 아니라 `credential.helper=osxkeychain`이었다.** 08-02에 "gh 토큰 invalid"로 진단했는데, 실측하니 gh 토큰은 유효하고(repo 스코프 보유) 키체인에 github.com 항목도 있었다. 문제는 **크론에 키체인을 열어줄 GUI 세션이 없다**는 것 — helper가 조용히 빈 응답을 내고 push가 username을 묻다 죽는다. 07-27~08-09 사이 41회 실패 / 0회 성공. → 해결: `gh auth token`을 `~/.git-credentials`(600)에 넣고 push를 `git -c credential.helper=store`로 명시. 검증은 `git -c credential.helper=store` + `GIT_TERMINAL_PROMPT=0`로 **키체인을 배제한 상태**에서 해야 의미가 있다 — 대화형 push 성공은 부모 세션 컨텍스트를 상속하므로 증거가 못 된다.
- **로컬 크론과 GitHub Actions가 같은 발행을 이중으로 돌면 매 실행 `_published.json`이 충돌한다.** 인증을 고쳐도 diverge 때문에 push가 계속 막힌다. 발행 URL 목록은 중복 방지 원장이라 **양쪽 합집합이 정답** — 스크립트가 이 파일만 자동 병합하고, 다른 파일이 충돌하면 사람에게 넘기고 중단하게 했다.
- **crontab 수정은 이 환경에서 에이전트가 할 수 없다** (macOS 권한). 긴 경로를 인자로 주면 조용히 잘려 엉뚱한 에러가 난다. 크론 등록·수정은 대표 수동 작업으로 남긴다.

- **캔버스 그래프에서 라벨을 노드 페인터 안에 그리면 나중에 그려진 노드가 앞 라벨을 덮는다.** 지식맵의 "Anthropic"이 "Anth"로 잘려 보인 원인이 이것 — 텍스트 자체는 온전한데 뒤이어 그려진 원이 위를 덮었다. `onRenderFramePost`로 라벨만 마지막에 한 번에 그리면 모든 텍스트가 모든 원 위에 온다. → 교훈: **캔버스는 그리는 순서가 곧 z-order다. 텍스트는 별도 패스로 분리한다.**
- **`zoomToFit`을 전체 노드로 부르면 외곽 고립 노드 몇 개가 줌을 지배해 본체가 작아진다.** 개선 전보다 나빠졌다. 노드 필터(`type==='tag' && val>=4`)를 주면 핵심 군집에 맞춰진다.
- **태그 696개 중 473개(68%)가 기사 1건짜리였다.** 자동 태깅이 매 기사마다 새 태그를 만들어 그래프를 노이즈로 채웠다. 연결이 없는 태그는 정보가 아니다 — `minTagCount=2`로 노드가 1,100 → 625로 줄었다. 태그 품질(예: "AI 정책"과 "AI정책" 중복)은 별도 과제로 남아 있다.

## 2026-08-02 주간

- **크론 발행이 "생성·커밋 ✅"인데 라이브가 안 바뀌었다 — push 자격증명이 조용히 만료돼 있었다.** 07-26에 "cron 발화·생성 확인"까지만 검증하고 발행 재개로 보고했는데, 정작 `publish-local.sh:88`의 `git push`가 매 실행 `could not read Username for github.com`으로 실패해 07-29 이후 13커밋이 로컬에만 갇혔다. gh 토큰 invalid + SSH publickey 거부 + keychain에 github.com 항목 없음 — 세 경로 모두 죽어 있었다. 대화형에서 push가 되던 건 부모 Claude Code 프로세스 컨텍스트를 상속했기 때문(07-26 CLI 인증 교훈과 정확히 같은 구조). → 교훈: **파이프라인의 "완주"는 생성·커밋이 아니라 `origin/main`이 실제로 전진했는지로 판정한다.** `git rev-list --count origin/main..main`이 0이 아니면 발행은 실패다. 검증은 항상 마지막 관문(라이브/origin)에서 건다.
- **push는 스크립트에서 실패해도 종료코드가 삼켜지면 로그가 초록으로 끝난다.** `publish-local.sh`가 `git push` 실패를 검사하지 않아 로그 마지막 줄이 `✓ pushed`(실제론 실패 직전 라인)로 남았다. 07-29 LESSONS의 "로컬 로그가 성공이어도 라이브가 안 바뀌면 실패" 원칙이 이번에도 그대로 재현 — 이번엔 커밋 게이트가 아니라 push 종료코드였다. → 교훈: **자동화의 모든 외부 관문(push/deploy)은 종료코드 검사 + 잔여 미푸시 카운트로 fail-loud 해야 한다.** 무성한 실패가 조용한 성공보다 낫다.
- **주간 PM은 지표뿐 아니라 `git status -sb`의 ahead/behind를 매주 실측한다.** 07-19에 이어 이번에도 최대 발견은 지표 쿼리가 아니라 `ahead 13`이었다. 커밋 로그만 보면 매일 발행이 도는 정상 프로젝트로 보인다 — origin과의 diverge를 봐야 라이브 정지가 드러난다.

## 2026-07-29

- **파이프라인을 "조각으로" 검증하고 완주시켰다고 착각했다.** 07-26에 크론을 배선하면서 `generate-news`만 따로 돌려 3쌍 생성을 확인하고, 기사는 **수동으로 복사해 `git add`로 커밋**한 뒤 "발행 재개"라고 보고했다. 그래서 바로 다음 단계인 `publish-local.sh`의 커밋 게이트를 한 번도 통과시켜보지 않았고, 거기 있던 버그(untracked 미감지)를 못 봤다. 결과: 크론 13회가 전부 정시 실행·생성 성공했는데 **push는 0회**, 기사 36개가 로컬에 갇힌 채 3일이 지났다. → 교훈: **자동화를 "돌아간다"고 말하려면 스크립트 전체를 처음부터 끝까지 한 번은 그대로 완주시켜야 한다.** 중간 단계만 따로 검증하고 나머지를 손으로 대신해주면, 손으로 대신해준 그 지점이 정확히 사각지대가 된다.
- **`git diff`는 새 파일을 못 본다 — 생성형 파이프라인의 커밋 게이트에 쓰면 안 된다.** `git diff --quiet -- src/content/news`는 tracked 파일의 수정만 보므로, 매번 새 파일을 만드는 발행 파이프라인에서는 **항상 "변경 없음"** 이 된다. 정작 바로 다음 줄의 카운터는 `git status --porcelain`으로 `^??`를 세고 있어 의도와 게이트가 어긋나 있었다. → 교훈: 새 파일이 산출물인 스크립트는 반드시 `git status --porcelain`으로 판정한다.
- **로컬 로그가 "성공"이어도 라이브가 안 바뀌면 실패다.** 이번 사고에서 `ai-guide-publish.log`는 매 회차 `✓ 3 article pair(s) written`으로 끝나 정상처럼 보였다. 실제 고장은 그 다음 줄에 있었다. → 교훈: **감시는 로컬 로그가 아니라 라이브 산출물 기준으로 건다.** 생성·커밋·푸시·배포 중 어디가 끊겨도 "라이브가 안 바뀐다"로 수렴하기 때문이다. `~/.claude/scripts/team/publish-watchdog.sh`(하루 2회, 이상 시에만 `main-checklist` 포스트)를 이 원칙으로 배선했다.

## 2026-07-26

- **`claude` CLI 구독 인증은 비대화형(cron)에서 상속되지 않는다.** 대화형 셸에서 `claude -p`가 멀쩡히 동작하길래 "로그인 문제 해결됨"으로 판단했는데, cron에서 돌리니 기사마다 `claude CLI exit 1`, 최소 환경 재현 시 `Not logged in · Please run /login`. **되던 이유는 부모 Claude Code 프로세스의 컨텍스트를 상속받아서였고, cron엔 그 부모가 없다.** `~/.claude/.credentials.json`이 존재해도 macOS에선 Keychain을 우선 보는 듯하며 Keychain은 로그인 세션에 묶인다. → 교훈: **"내 셸에서 되니까 크론에서도 되겠지"가 이 CLI엔 통하지 않는다.** cron용으로는 `claude setup-token`의 장기 토큰(`CLAUDE_CODE_OAUTH_TOKEN`)을 env로 주입해야 한다. 07-19 LESSONS의 "CLI 미로그인"도 실은 같은 현상이었을 가능성이 크다.
- **크론은 등록이 아니라 "실제 발화 + 완주"까지 봐야 검증이다.** 임시 프로브(2분 뒤 실행)를 넣어 확인하니 (1) 1차: PATH에 homebrew가 없어 `npm: command not found`, (2) 2차: PATH 고치니 RSS 9/9까지 가고 생성에서 인증 실패 — **등록만 보고 끝냈으면 두 실패 모두 다음 정규 실행까지 조용히 묻혔다.** → 교훈: 크론을 걸면 반드시 프로브로 끝까지 돌려보고, 로그에 성공 라인이 찍히는 것까지 확인한다.
- **같은 머신에서도 스케줄러에 따라 ~/Desktop 접근 가부가 갈린다.** 발행을 launchd로 등록하니 `bash: scripts/publish-local.sh: Operation not permitted`(TCC)로 즉사했는데, **crontab에 등록된 작업은 같은 경로를 문제없이 실행한다** — `venture-cycle.sh:180`이 Desktop 하위 워크트리에서 `bash scripts/verify.sh`를 돌려 매일 성공하는 게 증거. → 교훈: **이 워크스페이스에서 Desktop 하위 스크립트를 스케줄링할 땐 launchd가 아니라 crontab을 쓴다.** launchd로 걸면 조용히 아무것도 안 하고, 로그조차 안 남는다.
- **이미 main에 흡수된 auto 브랜치 하나가 야간 사이클을 3주간 차단했다.** `venture-cycle.sh:46`은 `feature/auto-*` 브랜치가 하나라도 있으면 "사람 확인 대기"로 그 프로젝트를 통째로 skip한다. 문제의 브랜치는 코드가 이미 main에 전부 반영돼 실질 diff가 0이었는데도 이름만 남아 매일 skip을 유발했다(trend-radar도 동일). → 교훈: **auto 브랜치는 main 반영 후 반드시 삭제한다.** 남겨두면 "확인 대기"가 아니라 무기한 정지다. 사이클이 skip 로그를 남겨도 그건 매일 같은 줄이라 눈에 안 띈다.
- **로컬 main과 origin/main에 각각 다른 게 갇혀 있었다.** 로컬엔 야간 사이클 코드 12커밋(아카이브 라우트 등)이 push 안 된 채, origin엔 CI가 커밋한 기사 22건이 pull 안 된 채로 3주를 보냈다. 양쪽 다 "정상"으로 보였고 로컬 브랜치만 보면 기사가 사라진 것처럼 보였다. → 교훈: **diverge를 커밋 수로만 보지 말고 어느 쪽에 무엇이 있는지 내용으로 볼 것.** 이 경우 정답은 한쪽 버리기가 아니라 rebase(둘 다 보존)였다.
- **jest가 리포 안의 `.worktrees/`까지 수집해 23건이 거짓 실패했다.** 워크트리의 `@/` 별칭이 메인 rootDir로 풀려 통과 자체가 불가능한 실패다. eslint엔 이미 같은 ignore가 있었는데 jest엔 없었다. → 교훈: **worktree를 리포 안에 두는 이상 모든 도구(eslint·jest·tsc)에 일괄 ignore가 필요하다.** 하나라도 빠지면 "테스트 깨짐"으로 오진한다.
